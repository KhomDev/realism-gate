# Precision: how often a flag is right

A flag is only useful if it is usually right. For v0.2.0 a sample of what each
rule flags was read in context and labelled, on three pinned corpora, for both
0.1.0 and 0.2.0. This page states what that measured and what it did not.
Every number here is generated by `eval/precision.py` into
[`eval/results/precision.md`](../eval/results/precision.md); the method,
the label definitions and the reproduce command are in
[`eval/README.md`](../eval/README.md).

## The corpora

| Corpus | Files | What it is | Seen while writing the 0.2.0 fix? |
|---|---:|---|---|
| in_sample | 891 | DeFiHackLabs `src/test`, the commit 0.1.0 was built against | yes |
| later | 70 | files added to DeFiHackLabs after that commit | yes: labelled before the fix, but two fixed patterns were first seen here |
| fresh | 57 | DeFiVulnLabs `src/test`, local-deployment demos | no: opened after the rule logic was frozen (commit `e9bea03`) |

Per rule and corpus, up to 30 flags were drawn with a committed seed, or all
of them when there were 30 or fewer. Only RG08 ever had more.

## Results

Precision is TP / (TP + FP); the bracket is the Wilson 95% interval. A rule
with one or two labelled flags has an interval too wide to mean much, and the
table says so by showing it.

### In-sample (DeFiHackLabs, 891 files)

| Rule | 0.1.0 | 0.2.0 |
|---|---|---|
| RG01 attacker-holds-privilege | 1/1 = 100% [21-100] | 1/1 = 100% [21-100] |
| RG02 privileged-step-in-exploit | 15/15 = 100% [80-100] | 15/15 = 100% [80-100] |
| RG04 storage-write | 7/7 = 100% [65-100] | 7/7 = 100% [65-100] |
| RG05 code-replacement | 2/4 = 50% [15-85] | 2/4 = 50% [15-85] |
| RG08 no-assertion (30 of 611 sampled) | 30/30 = 100% [89-100] | 30/30 = 100% [89-100] |
| RG10 no-baseline | 2/5 = 40% [12-77] | 2/2 = 100% [34-100] |
| RG11 unpinned-fork | 1/1 = 100% [21-100] | 1/1 = 100% [21-100] |

### Later additions (70 files; a second tuning set, not held-out)

| Rule | 0.1.0 | 0.2.0 |
|---|---|---|
| RG02 | 0/1 = 0% [0-79] | 0/1 = 0% [0-79] |
| RG07 mocked-call | 1/1 = 100% [21-100] | 1/1 = 100% [21-100] |

| RG10 | 2/8 = 25% [7-59] | 1/1 = 100% [21-100] |

The RG10 change removed six false positives here and one true positive.

### Fresh corpus (57 files; never used for tuning)

| Rule | 0.1.0 | 0.2.0 |
|---|---|---|
| RG05 | 0/1 = 0% [0-79] | 0/1 = 0% [0-79] |
| RG08 (30 of 55 sampled) | 30/30 = 100% [89-100] | 30/30 = 100% [89-100] |
| RG11 | 1/1 = 100% [21-100] | 1/1 = 100% [21-100] |

0.1.0 and 0.2.0 raise exactly the same flags here. RG10 does not fire on this
corpus at all, so **the RG10 fix has no out-of-sample measurement**: it is
graded only on data that was in view while it was written.

## What changed because of it

**RG10 (no-baseline).** Every false positive had the same cause: the test had
fixed the starting balance itself, so an absolute read after the attack was
already a difference. The forms seen were `deal()`/`vm.deal` of the measured
account before the attack, a shared logging modifier that zeroes the
attacker's ether through an internal getter, a contract the test deployed and
funded with one token being treated as non-fresh for every other token, and
the test contract's own token balances. 0.2.0 recognises all four. It still
flags `> 0` over a funded balance, a literal bound below a literal funded
amount, and the test contract's ether (Foundry funds it).

The cost: one true positive is gone. A test that asserts `WETH > 0` on an
account it dealt WETH, alongside other assertions that do have a baseline, is
no longer flagged, because RG10 stays silent on a test once any of its
assertions has a baseline. That behaviour is unchanged from 0.1.0; before the
fix the other assertions did not count as baselined, which is why it fired.

**RG05 (code-replacement) is now a warning, never an error.** Pooled over the
corpora it was right on 2 of 5 flags. Release ruling R3 says a rule under 80%
on the labelled sample does not ship as error. The wrong flags recreate the
attacker's own historical contract at its address, or install a chain-wide
system contract a local chain lacks; from the test source alone those look the
same as replacing the protocol's code, and no fix was attempted that would
only have fit these files.

**RG02** is under 80% on the later set, on a single flag (a fresh key whose
name contains a role word, registering itself). It is a warning already, so
R3 changes nothing. Its interval [0-79] is one data point.

No rule was added. See "Candidates" below.

## What this does not measure

- **Recall.** Nothing here says how many real problems the rules miss. That
  needs PoCs labelled as defective whether or not a rule fired, which this
  evaluation does not have. No recall figure is given anywhere for that
  reason.
- **Rules that never fired.** RG03, RG06, RG09 and the declaration rules
  RG12-RG14 raised nothing on any corpus. Their precision is unknown, and
  their severities are unchanged from 0.1.0.
- **Bounty PoCs.** All three corpora are public reproductions or teaching
  demos, not submissions with known triage outcomes.
- **Inter-rater agreement.** One reader labelled everything (see
  `eval/README.md`, "Who labelled").

## Candidates not shipped

- *Assert-greater-than-zero over a funded balance as a rule of its own.* Seen
  once (later set). Too rare to measure.
- *RG05: tell an attacker's historical contract from a protocol contract.*
  Three instances across corpora. The heuristics considered (the address's
  name, whether the new code is a contract written next to the test) would
  also hide the two true positives, which have the same shape. None was
  implemented.
- *RG02: a fresh `makeAddr` key is not a role holder unless granted one.*
  One instance; it conflicts with local-deployment tests where the protocol
  is deployed with that key as owner.

## Rust (Solana) tests

Not measured. Every figure above is for Solidity: the Rust frontend is new in
0.3.0, and there is no public, labelled collection of Solana PoCs comparable
to DeFiHackLabs to measure it on. Until there is, treat a Rust finding as a
question to answer, not a verdict.

What was checked instead, before release: the frontend was run over
[LiteSVM](https://github.com/LiteSVM/litesvm) at `c848c56` and five
[solana-program-library](https://github.com/solana-labs/solana-program-library)
test directories at `264ca72` (`token-lending`, `stake-pool`, `governance`,
`token-swap` and `single-pool`, each `program/tests`):

```bash
realism-gate check <checkout> --format json --fail-on never --no-config --no-declaration
```

All 164 Rust files parsed, and 451 tests drove a harness and were checked,
in under a second per repository. These are program test suites, not
PoCs, so a privileged signer or a hand-built account in them is often the
point of the test. Reading every finding found four patterns that were wrong
on their own terms, each now fixed and pinned by a test in `tests/rust.rs`:
a library method inlined as a fixture method of the same name, a keypair's
`.pubkey()` read as a fixed address, an attacker's own attempt to grant
itself a role reported as the harness granting it, and a user's
`owner: alice.pubkey()` field read as a role.
