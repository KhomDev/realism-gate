# Precision: how often a flag is right

A flag is only useful if it is usually right. For v0.2.0 a sample of what each
rule flags was read in context and labelled, on three pinned corpora, for both
0.1.0 and 0.2.0. This page states what that measured and what it did not.
Every number here is generated by `eval/precision.py` into
[`eval/results/precision.md`](../eval/results/precision.md); the method,
the label definitions and the reproduce command are in
[`eval/README.md`](../eval/README.md).

## The corpora

| Corpus | Files | What it is | Seen while writing the 0.2.0 fix? |
|---|---:|---|---|
| in_sample | 891 | DeFiHackLabs `src/test`, the commit 0.1.0 was built against | yes |
| later | 70 | files added to DeFiHackLabs after that commit | yes: labelled before the fix, but two fixed patterns were first seen here |
| fresh | 57 | DeFiVulnLabs `src/test`, local-deployment demos | no: opened after the rule logic was frozen (commit `e9bea03`) |

Per rule and corpus, up to 30 flags were drawn with a committed seed, or all
of them when there were 30 or fewer. Only RG08 ever had more.

## What changed because of it

**RG10 (no-baseline).** Every false positive had the same cause: the test had
fixed the starting balance itself, so an absolute read after the attack was
already a difference. The forms seen were `deal()`/`vm.deal` of the measured
account before the attack, a shared logging modifier that zeroes the
attacker's ether through an internal getter, a contract the test deployed and
funded with one token being treated as non-fresh for every other token, and
the test contract's own token balances. 0.2.0 recognises all four. It still
flags `> 0` over a funded balance, a literal bound below a literal funded
amount, and the test contract's ether (Foundry funds it).

The cost: one true positive is gone. A test that asserts `WETH > 0` on an
account it dealt WETH, alongside other assertions that do have a baseline, is
no longer flagged, because RG10 stays silent on a test once any of its
assertions has a baseline. That behaviour is unchanged from 0.1.0; before the
fix the other assertions did not count as baselined, which is why it fired.

**RG05 (code-replacement) is now a warning, never an error.** Pooled over the
corpora it was right on 2 of 5 flags. Release ruling R3 says a rule under 80%
on the labelled sample does not ship as error. The wrong flags recreate the
attacker's own historical contract at its address, or install a chain-wide
system contract a local chain lacks; from the test source alone those look the
same as replacing the protocol's code, and no fix was attempted that would
only have fit these files.

**RG02** is under 80% on the later set, on a single flag (a fresh key whose
name contains a role word, registering itself). It is a warning already, so
R3 changes nothing. Its interval [0-79] is one data point.

No rule was added. See "Candidates" below.

**Read the first impact row as the out-of-sample number.** The nine misses
(profit computed into a local before the assertion) were found on this same
120-pair set and then fixed, so the 98.9% is measured on data that shaped the
fix. It is in-sample. A fresh held-out set is the only way to replace the
91.0%; the 2026-11-24 re-run reproduces it but does not make it out-of-sample.

Caveats, from the same report:

- **The attacker field is NOT interpretable.** The rubric labels identity by
  address-literal presence while the tool checks how the caller is bound, so
  no attacker precision is claimed. The label defect is published, not hidden.
- **`amount` is NOT CHECKABLE by design.** The record states a fiat loss; the
  PoC asserts token balances. All 120 amount rows are not checkable.
- **`asset` is NOT INTERPRETABLE with this corpus.** The record names a coarse
  asset, and the tool's predicate is a name match; a label built from the same
  text would be circular.
- **`preconditions`, `cited` and `fix` are NOT CHECKABLE here.** The incident
  records state no preconditions, carry transaction/analysis links rather than
  contract citations, and contain no patches; `check` never applies a patch.
- **Two rows are a recall cost, not precision.** The tool marked
  PikeFinance_exp.sol and SWAPPStaking_exp.sol `shown` while the rubric sees no
  evidence. They are not in the precision ratio, so 98.9% is not an upper bound
  on correctness; re-read them before quoting it. One further row (AzukiDAO)
  was flagged not shown against a label gap, also outside the ratio.
- **The three rejection-row fixtures (R-034/35/36)** are pointers plus expected
  status only; their inputs are private and not in this repo.

Quote both impact rows, or the first one; never the 98.9% alone.

**Release provenance.** The original measurement was made on the 1.0.0 feature
tree released as tag `v1.0.0`, commit
`11703a31a7a0fde11d02062222bab152e0d89f5e` (debug binary `06eb73f2…`). The
2026-11-24 re-run used the 1.0.4 release binary named above; the claim-binding
predicates are unchanged, and `eval/claims/results.json` records the tool,
sha256 and date. The tag is the durable provenance for the original run; a
debug hash identifies a measured build, and a release-profile binary hashes
differently.

## What this does not measure

- **Claim binding beyond the impact field.** The scorecard publishes every
  field, but only impact is scored: attacker and asset are not interpretable
  with this corpus, and amount, preconditions, cited and fix are not checkable.

- **Recall.** Nothing here says how many real problems the rules miss. That
  needs PoCs labelled as defective whether or not a rule fired, which this
  evaluation does not have. No recall figure is given anywhere for that
  reason.
- **Rules that never fired.** RG03, RG06, RG09 and the declaration rules
  RG12-RG14 raised nothing on any corpus. Their precision is unknown, and
  their severities are unchanged from 0.1.0.
- **Bounty PoCs.** All three corpora are public reproductions or teaching
  demos, not submissions with known triage outcomes.
- **Inter-rater agreement.** One reader labelled everything (see
  `eval/README.md`, "Who labelled").

## Candidates not shipped

- *Assert-greater-than-zero over a funded balance as a rule of its own.* Seen
  once (later set). Too rare to measure.
- *RG05: tell an attacker's historical contract from a protocol contract.*
  Three instances across corpora. The heuristics considered (the address's
  name, whether the new code is a contract written next to the test) would
  also hide the two true positives, which have the same shape. None was
  implemented.
- *RG02: a fresh `makeAddr` key is not a role holder unless granted one.*
  One instance; it conflicts with local-deployment tests where the protocol
  is deployed with that key as owner.

## 0.5.0

The 0.1.0 / 0.2.0 tables above are unchanged. They were not re-labelled.
0.5.0 adds four rules and changes RG03's severity. The new flags were
labelled by one reader, the same way as the 0.2.0 set, and are in
`eval/labels/v0.5.0.jsonl`. `eval/results/precision.md` has the table.
What follows is what that table says, and the RG03 count that is not in it
because the rule raised nothing on these corpora.

### RG03, before and after

On the three pinned corpora RG03 raised **0** flags in 0.2.0 and **0** in
0.5.0 (no warning, no note). Fork reproductions do not leave the test
contract as the sender of a call on a contract it deployed.

The noise the change is for is local deployment. On the six review PoCs in
`tests/fixtures/review/` (the files an external review ran, where 0.4.0
reported RG03 nine times, all on the ordinary `new Protocol()` pattern):

| | Warnings | Notes |
|---|---:|---:|
| 0.4.0 (every non-read call the deployer makes) | 9 | 0 |
| 0.5.0 (warning only when the call is named like an access-controlled function) | 0 | 9 |

All nine are the same lines. None of them calls `sweep`, `set*`, `pause`, or
another name the rule treats as gated. The run that fails on warnings no
longer fails for those nine. The note is still emitted, so the pattern is
visible.

That 9-to-0 is a count of severity changes on one set of files, not a
precision. Those files were in hand while the severity split was written.

### The new rules, labelled

Precision is TP / (TP + FP) on every flag, because none of these rules raised
more than 30. The bracket is the Wilson 95% interval. One reader. Pending a
second.

| Rule | in_sample (891) | later (70 new files) | fresh (57) |
|---|---|---|---|
| RG15 profit-ignores-costs | 0/1 = 0% [0-79] | — | — |
| RG16 implausible-amount | 0/1 = 0% [0-79] | — | — |
| RG17 unevidenced-setup | 2/9 = 22% [6-55] | 0/2 = 0% [0-66] | — |
| RG18 revert-only | 2/2 = 100% [34-100] | 0/1 = 0% [0-79] | 0/7 = 0% [0-35] |

All four ship as warnings. RG17 and RG18 are under 80% once the corpora are
pooled (RG17 is 2 of 11, RG18 is 2 of 10). Release ruling R3 would have
forbidden shipping either as an error. They are not errors.

What the wrong flags were:

- **RG15.** One flag. A helper computes `amountInWithFee` for an AMM quote.
  The asserted profit is a token balance, which is already net of that fee.
  The rule saw a computed fee and a profit that does not subtract it.
- **RG16.** One flag. `this.mint(type(uint256).max)` mints the attacker's own
  token. The max mint is the exploit. The bound cannot tell an attacker-minted
  token from a forged balance of someone else's.
- **RG17.** Nine of eleven flags are the attacker's own contract
  (`MaliciousToken`, an exploit helper) whose name matches a stand-in. Two
  are a bridge the test constructs and labels local. Those two are the
  pattern the rule is for. The nine are the attacker deploying their own
  contract, which an attacker can do.
- **RG18.** On the fresh corpus every flag is a teaching test whose claim is
  the revert (a fixed path, or a denial of service). On the hack corpus, two
  flags are real: the impact is only logged, and the only assertion is a
  revert about something else. One later flag is a negative control whose
  claim is the revert.

### What 0.5.0 still does not catch on its own

A postmortem profit that depends on a maker strategy nobody deploys is
RG17 only when the test calls `ship`, `dock` or `push`, or deploys a type
named like a strategy or a hook. A strategy built as raw bytecode and shipped
through a call of another name is not seen. A fee that wipes the profit is
RG15 only when the test says so, in a computed fee variable or in the words
"fee drag" / "must not profit" / "under fee". A comment that mislabels a unit
is not RG16. A call the protocol's README forbids is not visible unless the
author cites that README under `deployment.evidence` or the call is one of
the names above. Those limits are also on the rule pages, under "How it can
be wrong".

### What was checked before the P1 measurement

Before 1.0, the frontend was run over [LiteSVM](https://github.com/LiteSVM/litesvm)
at `c848c56`, [solana-program-library](https://github.com/solana-labs/solana-program-library)
at `264ca72`, [Anchor](https://github.com/coral-xyz/anchor) at `33868ff` and
[program-examples](https://github.com/solana-developers/program-examples) at
`c0cafc5`. At `264ca72`, only `token-lending` and `governance` have a
`program/tests` directory; the earlier text's claim of five directories
(`stake-pool`, `token-swap` and `single-pool` included) was wrong for that
commit and is corrected here. All discovered Rust and TypeScript files parsed;
451 Rust tests and 292 TypeScript tests in 118 suites drove a harness and were
checked. These are program test suites, not PoCs, so a privileged signer or a
hand-built account is often the point of the test.

Reading every finding found four Rust patterns and five TypeScript patterns
that were wrong on their own terms, each now fixed and pinned by a test in
`tests/rust.rs` and `tests/typescript.rs`: a library method inlined as a
fixture method of the same name; a keypair's `.pubkey()` read as a fixed
address; an attacker's own attempt to grant itself a role reported as the
harness granting it; a user's `owner: alice.pubkey()` field read as a role;
the provider wallet counted as the signer of every transaction it only paid
for; `assert.ok(false)` after a call that should throw read as a tautology; a
flag set by an event callback read as a constant; a `localhost` URL held in a
constant read as a live cluster; and a helper read labelled `"Beginning"` and
`"Resulting"` not seen as a before-and-after pair. A setup test titled
`airdrop payer` is now read as setup too.
